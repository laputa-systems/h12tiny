## Decisions

**Owner (from the draft, binding):**

- The campaign is local only: no challenge PR, leaderboard contact, or public deployment.
- The primary benchmark exercises h12tiny's own server, router, and bodies. The h12tiny application adds no Tokio, Axum, Tower, hyper-util, Reqwest, or other HTTP framework.
- The h12tiny library is not optimized until the baseline is saved (P3). A real library defect that blocks the challenge is fixed first, separately, with a failing regression test, in its own commit.
- A redesign of the fundamentals (HTTP/connection path or storage path) is permitted if it is simpler and materially faster, but only after the current design meets a reasonable floor. For this campaign the floor is the completed parity and measurement work: the 42 checks green, M1–M4 accepted with a measured local baseline, and M4's attribution in hand. A redesign is not O1 and needs a fresh owner decision; a disappointing comparison is not by itself authorization to start one.
- `bench/load.js`, its thresholds, ramp shape, and think times, the challenge tests, seed generator, and schema are never modified or copied into a private variant.

**Prescribed (reverse only on the stated evidence):**

- **D1 Pins.** The challenge repo and h12tiny are already at the pinned revisions above (checked 2026-11-01); do not refresh. `setup.sh` holds the challenge revision as its single constant and clones into `.work/twelve-dollar/challenge`. Every result directory records `git rev-parse HEAD` of h12tiny, the challenge checkout, and whether the tree was dirty.
- **D2 Layout.** `benchmarks/twelve-dollar/` has its own `[workspace]` table, because a nested package without one fails with "current package believes it's in a workspace when it's not" (reproduced). Members, each under `benchmarks/twelve-dollar/crates/`: `app-core` (SQLite, JWT, JSON, validation; no HTTP), `h12tiny-app` (the server bin `h12tiny-twelve` and the static diagnostic bin `h12tiny-static`), `axum-ref` (reference server; the only crate allowed Tokio and Axum; nothing depends on it), `attribution` (SQLite-only and microbenchmarks). Add `"benchmarks"` to the root package's `exclude` so the published `h12tiny` tarball does not carry it (`cargo package --list` shows `scripts/`, `docs/`, and `examples/` entries today). The benchmark `Cargo.lock` is committed. The root `rust-toolchain.toml` pin (`nightly-2026-09-15`) applies to the benchmark and is not changed.
- **D3 Dependencies**, benchmark workspace only: `rusqlite` with `bundled` (the same SQLite on macOS and Ubuntu, no system library; needs a C compiler), `serde` and `serde_json` (ordinary serializer, struct field order), `hmac` and `sha2` with `Mac::verify_slice` (constant-time compare) and the workspace's `base64` for JWT, `signal-hook` or a crate already in the tree for SIGTERM, `criterion` as a dev-dependency only if manual loops do not suffice. The gates: `sh scripts/check-normal-dependencies.sh` stays green and the root `cargo tree --features full` does not change, `cargo tree -p h12tiny-app -e normal` contains none of `tokio`, `axum`, `tower`, `hyper-util`, `reqwest`, and the h12tiny application adds no `unsafe`. Build time and binary size of the benchmark app are not gated. Any further dependency needs a one-line reason in the README.
- **D4 Server configuration** (both modes, same code): `h12tiny::server::serve(...).with_bounds(ProductionBounds { max_connections: 30_000, header_read_timeout: Some(75 s), drain_timeout: Some(30 s) })`. Evidence: `Serve::production()` caps at 1024 connections and arms a 10 s header-read timer (`crates/h12tiny-server/src/lifecycle.rs:94-101`); that timer is armed in `poll_read_head`, which an idle keep-alive connection also reaches (`crates/laputa-hyper-futures-lite/src/proto/h1/conn.rs:224-240`, `:262-272`). So the preset likely closes idle connections after 10 s, against the spec's 65 s minimum. R1 proves this by test; if an idle connection survives 66 s under `production()` the 75 s override is unnecessary and the bound is whatever R1 shows is safe. The timer stays non-`None` so slow-header clients stay bounded. Do not change the library preset; report it as a finding (see Needs owner). The router is `Router::new()` with a 64 KiB `body_limit` on the POST routes, no handler timeout, and `fallback` returning `404 {"error":"not found"}`. Path ids arrive as `Path<String>` and the app parses them, so `abc`, `0`, `-1`, `1.5` produce the spec's 400 body.
- **D5 SQLite and concurrency.** Never block executor threads on SQLite. N reader OS threads each own a read connection, and one writer thread owns the write connection. Handlers send a bounded request and await a `futures-channel` oneshot reply. Pragmas: `journal_mode=WAL`, `synchronous=NORMAL`, `busy_timeout` 5000 ms, default cache. Use `prepare_cached`. No response, query-result, or JWT caching of any kind. No group commit in the baseline. Delegated: N in 1..=4, chosen by the smoke runs in M1 and recorded; the executor thread count is set explicitly and logged at startup, because `nproc` inside a 1-CPU container still reports 18 (reproduced) while Rust's `available_parallelism` follows the cgroup quota.
- **D6 Linux profile ("box").** Reference hardware is not available: the host is Apple M5 Max, macOS arm64, and the Docker (OrbStack) VM is aarch64 with 18 CPUs and 15.66 GiB. Emulated x86-64 is rejected as meaningless for CPU comparison. The local stand-in is native Ubuntu 24.04 aarch64 in Docker, labelled **non-comparable to the leaderboard**:
  - One container `h12t-twelve-box` from `ubuntu:24.04` (digest `sha256:fe81560990fae86dc4743202b2cb4d3df98d0bcf949173cecef15ce1127ef852`) runs nginx and the app together, as on the challenge machine. Flags: `--cpus=1 --memory=2g --memory-swap=2g --ulimit nofile=65535:65535`. The harness asserts `/sys/fs/cgroup/cpu.max` is `100000 100000`, `memory.max` is `2147483648`, and `memory.swap.max` is `0`, and stores the values.
  - k6 runs in a second container, `grafana/k6` pinned to `sha256:3e4186aea62e11a45560bfc51e19eeafe82fc07ce069c78aff44b7ff893d9a5e` (k6 v2.3.0, linux/arm64), with `--cpus=8 --memory=10g`, on the user network `h12t-twelve-net`, addressing the box by container IP (no published port or userland proxy). No `brew install`.
  - nginx comes from apt in the same image (1.24.0 at check time). `bench/nginx.conf` is mounted unchanged as a `conf.d` file. A harness-owned main config sets `worker_processes 1` (the default `auto` would start 18 workers here), `worker_rlimit_nofile 65535`, `worker_connections 16384` (stated in that file's header), and includes only `conf.d/*.conf`, so the distribution's default site cannot conflict with `default_server`. These are the only differences; list them in the report.
  - The seed lives on a Docker volume and each run copies it into a fresh per-run directory on a Docker volume (ext4 in the VM). Never a macOS bind mount (WAL shared-memory and locking semantics over the file-sharing layer would distort results) and never tmpfs (it counts against the 2 GiB and is memory-backed).
  - Builds happen in an unconstrained builder container sharing the cargo target and registry volumes with the box, so `build.sh` inside the box is a warm no-op. Release profile as in the root manifest (thin LTO, `panic = "abort"`), no `target-cpu=native`; record `rustc -Vv` and the flags.
  - Delegated: if `cpu.stat` shows `nr_throttled / nr_periods` above 5 % in a headline run, repeat that run with `--cpuset-cpus=<one core> --cpus=1` as well and report both, because quota throttling is not how a real vCPU behaves. Never use affinity alone.
- **D7 Profile A (macOS, directional).** Direct mode only (nginx runs only in the box): the server runs natively on the host under `/usr/bin/time -l` and is stopped with SIGTERM so CPU and peak RSS print at exit; k6 runs in the pinned container and reaches the host through `host.docker.internal`; `ulimit -n 65535` in the server's shell. Profile A is smoke only (50 and 500 VUs, 10 s ramp, 60 s hold) and its numbers never appear next to the box numbers as a comparison.
- **D8 Search protocol** (Mode A and Mode B each, in the box, fresh app process and fresh DB copy for every run, warm-up included):
  1. Warm-up: 1,000 VUs, 2 minutes, unscored.
  2. Probes: `VUS` starts at 2,500 and doubles; each probe uses `RAMP_UP=60s`, `DURATION=2m` (the leaderboard also uses 2-minute probes), then bisects to within 250 VUs. If 2,500 fails, halve until a pass and label the search modified.
  3. Confirm: the highest passing level gets a `DURATION=5m` hold, twice, each on a fresh DB. Score = the highest level where both holds pass; if either fails, step down 250 and repeat.
  4. A run passes only if k6 exits 0 and the run is valid (D9). At most 14 runs per mode.
  - **Ceilings.** Mode A cannot exceed 14,000 VUs (nginx `worker_connections 16384` bounds client connections, upstream connections also count). Mode B cannot exceed 25,000 VUs (one source address has about 28,000 ephemeral ports to one destination: range 32768-60999, reproduced in the container). Both are further capped by H3, the measured generator ceiling. A pass at a ceiling is reported "passes at the ceiling, generator-limited", never as the maximum; the leaderboard's top scores need several generators (Needs environment).
- **D9 Run validity.** Bracket every timed run with `perf-gate-ready` (must exit 0 before) and `perf-gate-ready -1` (right after); discard a run that overlapped load and repeat it. Hot processes belonging to the container runtime that executes the benchmark (OrbStack Helper here) are the run's own load and do not defer it; any other hot process does. A load-average failure still defers immediately. If the gate stays busy across 3 attempts at least 10 minutes apart, record "perf gate deferred: host busy", park that item on **Needs environment**, and continue with untimed work. A run is also invalid if: the k6 container exceeded 80 % of its CPU or memory allocation, k6 reported dropped iterations or fewer active VUs than the target, the app logged any `on_connection_rejected`, the challenge checkout is no longer clean, or the DB path existed before the run. An invalid run is repeated, never counted as a failure of the server.
- **D10 Metrics.** CPU per request = (app CPU seconds over the k6 window, from the `/proc/<pid>/stat` utime + stime delta; `time -l` on macOS) ÷ k6 `http_reqs` for that run. Nginx is measured the same way from its own pids and reported separately and combined. Sampling at 1 Hz into a CSV under the run directory: per-pid CPU, `VmRSS`/`VmHWM`, fd count, established sockets on the app port (`ss`), DB and WAL sizes, cgroup `memory.current`, `memory.peak`, and `cpu.stat`. Error categories come from the nginx access log status field (Mode A) and the app's shutdown summary line (connections accepted and rejected, responses by status), which is also the leak check: sockets return to baseline after ramp-down.
- **D11 Harness shape.** `run.sh` is the single outer entry point (`setup`, `test`, `smoke`, `search`, `confirm`, `attribute`, `report`, with `--profile macos|box` and `--mode nginx|direct`). Everything that runs inside the box (`box/*.sh`) is plain bash with no Docker knowledge, so the owner can run it unchanged on a native Ubuntu host. k6 results are read from `--summary-export` or an equivalent flag so `load.js` stays untouched; `jaq` parses them. Build the parser against a real run before trusting it.
- **D12 Docker hygiene.** Create only resources named `h12t-twelve-*`. Remove only those. Never `docker system prune`, never touch other containers, images, volumes, or networks. Delete per-run DB copies after the run's summary is saved (each is about 250 MB).
- **D13 Attribution fallbacks.** Prefer `perf record` and a flamegraph in the box. If `perf` does not work on the OrbStack kernel (`7.2.12-orbstack`), use `strace -c -f` if ptrace is permitted, and on macOS use `/usr/bin/sample`. Report which method was used. The CPU-per-request subtraction in M4 does not depend on a profiler.
- **D14 Optimization gate (O1).** Optimize only if M4 attributes at least 20 % of app CPU per request to h12tiny-owned work (HTTP parsing, connection management, routing, response construction). At most 3 changes. Each needs evidence first, no public API or default-limit change, no new dependency, and an interleaved A/B on CPU per request (`benchmark-checklist`); keep it only if the gain exceeds the observed run-to-run spread and is at least 3 %. Otherwise revert it and record why. If the share is under 20 %, write that finding and skip O1.

**Delegated (record in the README only if a later slice depends on it):** reader-thread count N (D5); the executor thread count; the exact nginx main-config text; the generator ceilings (H3); the shape of the static responses in the HTTP-only reference.

## Reference comparison (local, not a leaderboard score)

The local clone's `LEADERBOARD.md` scores every entry on a 1 vCPU / 2 GB Synteq VPS (Xeon Platinum 8260 at 2.4 GHz) with separate 16-core generators, a fresh database per probe, and a 5-minute hold; score = most users held with p95 < 500 ms, p99 < 1 s and errors < 1 %. Ours runs on the M5 Max / OrbStack box in D6, so hardware is not comparable; CPU per request and the request mix are the useful shape.

| Leaderboard top 15 | 240,000–295,000 | 23,000–28,000 | — | 26–34 | 5-min holds, 71–92 % CPU |

| Local direct cap, H3 | 25,000 | 1,866 | 0.86 / 1.57 ms | — | 60 s probe, k6 353 % / 67.3 % memory |

Local rows are 2-minute probes (M2), one 5-minute confirmation hold, and 60-second probes (H3). The 14,000 and 25,000 figures are local socket and port caps, not the server's ceiling: k6 stayed at 16 % and 44 % of its 800 % CPU allocation, so the generator was not saturated either. The sub-millisecond p99s come from running at 5–15 % of the box CPU, not from being faster at saturation.

What the numbers say: the top entries spend roughly 26–34 µs of app CPU per request; this app spends 76–85 µs (108–121 µs including nginx), about 2.5–3.4× more work per request, against leaders that use io_uring and direct SQLite B-tree reads. The local VU figure is not a score. M4 attribution must say how much of the 85 µs is h12tiny-owned before any optimization; D14's 20 % gate still applies, and a redesign waits for the floor above.

## Execution boundary and non-goals

**Authorized:** create and edit files under `benchmarks/twelve-dollar/`, the one-line `exclude` change to the root `Cargo.toml`, and library fixes or kept optimizations as described; clone the challenge repo once into `.work/twelve-dollar/challenge` and generate the seed there (its own `.gitignore` covers the outputs); run `docker` for `h12t-twelve-*` resources and pull the two pinned images and apt/rustup/crates.io packages inside containers; run the unchanged k6 against containers on this machine; commit locally to `main` in reviewable commits. Timed runs are expected to take about 1.5 h per mode (probes about 3.5 min each, holds about 6.5 min each); this is authorized. Scratch and worktrees live under `.work/`, never `/tmp`.

**Forbidden:** pushing; publishing or releasing; any PR, issue, or request to the challenge repo or its leaderboard; deploying to a public host; changing the challenge checkout, `load.js`, tests, seed, schema, or thresholds; changing the pinned nightly; running a formatter; committing seeds, tokens, binaries, traces, or raw result sets; changing public APIs, types, schemas, permissions, or default limits of library crates (park the item and list it under Needs owner).

**Non-goals:** `io_uring`, custom B-tree readers, generated C, caches, a new protocol engine, tuning the OS beyond what the challenge forbids, and claiming leaderboard parity.

**Contract changes:** none planned. Root `exclude` only changes packaging.

**Needs owner (does not block the campaign):** whether `Serve::production()` should stop applying its 10 s header-read timeout to idle keep-alive connections. Recommendation: document it in [limits](docs/limits.md) and add a separate idle-timeout bound later; the campaign only reports it.
